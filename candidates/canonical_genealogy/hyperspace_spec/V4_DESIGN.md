DIFFICULTY SOURCE: a seed-driven generator generator.py emitting gen(family,k,seed)->(prompt, exact_answer, oracle_ops). ## The winning design (concrete) — V4-PARAMETRIC — the Parametric Difficulty Ladder (a pre-declared generator + a known-hardness anchor) + PREDICT-half v0 

### V4 generator + metric
- **difficulty_source:** A SEED-DRIVEN PARAMETRIC GENERATOR `gen(family,k,seed)->(prompt,exact_answer,oracle_ops)` written and frozen (sha256 of generator.py logged) BEFORE any model call. Four families, each isolating ONE difficulty knob so difficulty = the knob, not the wording: (F1 MODARITH-CHAIN) evaluate a length-k chain of modular ops over Z_97, e.g. k=2: '((37+58) mod 97)*? ...'; knob=k reasoning steps (k in 2,4,6,8,10); exact integer answer in [0,96]; oracle_ops=k. (F2 BASE-MULTIPLY) multiply two n-digit integers, knob=operand bit-length b (b in 3,6,9,12,15 bits ~ 1..5 digits); exact product; oracle_ops=b*b (schoolbook partials). (F3 SAT-SELECT) a list of m candidate integers with d DISTRACTORS satisfying all-but-one of c constraints; knob=distractor count d (d in 1,3,5,8,12); exact answer=the unique full-satisfier; oracle_ops=m*c comparisons. (F4 NEST-PARENS) evaluate a depth-h nested arithmetic expression, knob=nesting depth h (h in 2,3,4,5,6); exact integer; oracle_ops=number of nodes in the parse tree. The pre-registered difficulty BAND of an item = the ordinal rank of its knob within its family (band 1..5), NOT an author guess. ANCHOR (the de-circularizing spine): a frozen ANCHOR_SET of ~12 hand-transcribed items with EXTERNAL published difficulty (GSM8K easy, MATH L1-L5 by their own level field, 2 AIME integers) — author-independent labels. The generator is VALIDATED, not tuned, against this anchor: oracle_ops per band is computed, and we require Spearman(oracle_ops_band, external_anchor_label) >= 0.7 on the overlap mapping (e.g. F1 k=2..10 mapped onto anchor L1..L5 by op-count quantile). If a family fails this anchor check it is rejected/re-specified before the run. This makes k EXOGENOUS: difficulty is the deterministic solver's op-count, anchored to externally-graded items, never my per-item taste.

- **preregistration:** A two-file commit made BEFORE the first model call, both hashed and timestamped: (1) generator.py (the gen() functions + the frozen ANCHOR_SET + the oracle solvers) — its sha256 is written to v4_preregister.json. (2) v4_preregister.json containing: the 4 family specs, the knob grid per family, the band=rank-of-knob mapping, the master_seed (one integer), the EXACT list of (family,k,seed) tuples to be generated (so the item set is fixed before generation), the anchor Spearman>=0.7 gate result, the effort metric definition, the run protocol (repeats/seeds), and the pre-declared pass/fail thresholds (PASS: per-provider Spearman(effort,band) >= 0.6, p<0.05 by permutation; FALSIFIER below). Because items are minted from (seed) AFTER the seed is committed, labels are fixed before any run and cannot be author-adjusted per item. The generator hash lets anyone re-mint the identical battery and confirm no per-item tuning occurred. predict_sealed analog: v4_preregister.json is append-only; a second 'unsealed' file with results is written only after the run, never overwriting the pre-registration.

- **effort_metric:** PRIMARY effort = gpt-5.5 vendor-reported `reasoning_tokens` (usage.completion_tokens_details.reasoning_tokens) — VERIFIED LIVE this session (returned 38 on the 2,6,12,20,30 sequence at effort=medium). This is the ONLY runner with a real vendor effort signal, so V4's effort axis is gpt-5.5-ONLY (claude output_tokens is flat=6 = answer length per v3_run.jsonl; gemini emits nothing; wall-seconds is BANNED by guardrail). To address the raw-token-count confound (the brief's r=-0.544: raw output length anti-correlates with difficulty because hard problems get TERSER final answers) we NEVER use output/completion tokens for effort — only the hidden reasoning_tokens, which is generation INTERNAL to solving, not answer verbosity. To address the Illusion-of-Thinking NON-MONOTONICITY (2507.04023: reasoning tokens can COLLAPSE past a complexity threshold as the model gives up), effort is recorded as a CURVE not a scalar: for each item we sweep reasoning_effort in {low,medium,high} and record (reasoning_tokens, correct) at each. The effort statistic entered into Spearman is EFFORT-TO-FIRST-VERIFIED-DISSOLVE = min reasoning_tokens over the sweep where correct==True (the V2 'first-correct' convention); if NO effort level solves it, the item is RIGHT-CENSORED at the ceiling (effort = ceiling-tokens, flagged exhausted) and handled by the non-monotonicity rule below. This makes effort the COST OF A CORRECT SOLUTION, immune to the give-up collapse (a collapse with a wrong answer is a censored point, not a low-effort point).

- **nonmonotonicity_handling:** Three pre-registered mechanisms so the Illusion-of-Thinking give-up collapse cannot silently invert the correlation: (1) RIGHT-CENSORING — items not solved at any effort level get effort=ceiling (the max reasoning_tokens observed in the sweep, marked exhausted=True), so a give-up (few tokens, wrong) is NOT recorded as 'easy/cheap'; it is recorded as 'maxed-and-failed' = hardest. The Spearman is computed on effort-to-first-correct with censored items pinned at the top of the effort rank. (2) MONOTONICITY DIAGNOSTIC reported alongside rho: per family, count band-pairs where median-effort inverts (higher band, lower effort-to-solve); a high inversion count is itself the reported signal that the collapse regime was entered (and which band it starts at = the knee). (3) DUAL READOUT — we report BOTH Spearman(effort,band) AND Spearman(solve-rate-decay, band): if reasoning_tokens go non-monotone past the knee but verified-dissolve RATE still falls monotonically with band, difficulty is confirmed by the solve-rate channel even where the token channel collapsed (demote 'effort tracks difficulty' to 'solve-rate tracks difficulty above the knee'). The knee location is a pre-registered observable, not a surprise.

- **protocol:** STEP 0 (pre-run, no model): write+hash generator.py; run the deterministic oracle solver on every (family,k,seed) to fill exact_answer + oracle_ops; run the ANCHOR gate (Spearman(oracle_ops_band, external_anchor_label) >= 0.7) — abort+respec any failing family; commit v4_preregister.json. STEP 1 (mint): from master_seed draw R=3 independent seeds per (family,k) -> 4 families x 5 bands x 3 seeds = 60 unique items, each with exact machine-checkable integer answer. STEP 2 (run): for each item, gpt-5.5 sweep reasoning_effort {low,medium,high} = 180 calls; verified-dissolve gate = last_int(reply)==exact_answer (reuse digestion_v2.verify/last_int verbatim); record reasoning_tokens + correct + exhausted at each level; TIMEOUT=100s ceiling. Repeats: the 3 seeds per band ARE the repeats (variance from instance, not just from sampling) PLUS optionally re-call medium effort 2x for sampling variance -> report both instance-variance and call-variance. STEP 3 (analyze, numpy-only, all primitives VERIFIED this session): per item effort=min reasoning_tokens at first correct (censored=ceiling if none). Compute (a) per-FAMILY Spearman(effort, band) with a 4000-perm permutation p-value (controls within-family so the correlation is not inflated by between-family scale differences — the cleanest test that the KNOB drives effort); (b) a pooled partial Spearman across families controlling for family id; (c) the monotonicity inversion count + knee per family; (d) the dual solve-rate-vs-band Spearman. Report each family's rho with CI (bootstrap over the 3 seeds). Cross-provider arm is EXPLICITLY DEFERRED (claude/gemini have no effort signal) — V4-parametric is the single-runner effort spine; the solve/fail matrix across all 3 runners can still be recorded for the universal-residue partition but is NOT part of the effort-Spearman claim.

- **falsifier:** PRIMARY FALSIFIER (demote-not-kill): per-FAMILY Spearman(effort, band) <= 0.3 (with permutation p>0.05) for the families whose anchor gate passed -> the parametric knob does NOT drive gpt-5.5 effort within a family where the borrowed-label confound is removed by construction -> DEMOTE 'effort tracks pre-registered parametric difficulty' to 'effort is dominated by family/surface, not by the isolated knob', and fall back to the solve-rate channel. SECONDARY (the de-circularizer's own falsifier): if the ANCHOR gate fails (Spearman(oracle_ops_band, external_anchor_label) < 0.7) for a family, that family is REJECTED before any run as not-defensibly-exogenous (the knob is not anchored to external hardness) — this is the mechanism that prevents circular self-tuning and is logged as a dated dead child. TERTIARY (saturation, the V3 mirror): if gpt-5.5 dissolves ALL bands at low effort (no spread, effort flat across band) the battery's TOP knob is too low for the 2026 frontier -> re-source the knob ceiling higher (k=20, b=30bits) — bounded iteration, not a dead end. QUATERNARY (collapse-masquerade): if effort rises then collapses (Illusion-of-Thinking) AND solve-rate ALSO stays flat-high, the non-monotonicity is benign; if effort collapses AND solve-rate falls, the knee is real and reported — only an UNDETECTED inversion (rho positive but driven by censoring artifact) is a true failure, guarded by reporting the inversion-count diagnostic.

### PREDICT-half
- **seal:** HASH-SEAL with blind construction, append-only. Per trial: the prediction record {trial_id, runner, family, k, context_C_sha256, target_T_sha256, R (the sealed forward answer), confidence c, derivation_channel, t_obs_iso} is appended to predict_sealed.jsonl and a running sha256 chain (each line's hash includes the previous line's hash, git-style) is written to predict_seal_chain.txt BEFORE T is ever scored or revealed to the scorer. The commit precedes the reveal (mirrors session_arc/build_bitemporal.py t_obs). v0 is honestly named INFORMATION-BLINDNESS (a withheld-field holdout), NOT a wall-clock future — the 'future' is that T is generated but withheld from the predictor's context C. The seal is the sha-chain (tamper-evident append-only), strictly stronger than the local-timestamp the external pass flagged as weak.

- **blind_construction:** C and T are minted by the SAME frozen parametric generator as V4, which is what makes the holdout genuinely blind and non-derivable. PLANT setup per family: the generator emits a FULL instance, then SPLITS it into (C = the rule + all-but-one operand/term, T = the withheld final operand AND its exact answer). Crucially C states the RULE but withholds the specific value that determines T, so T is NOT computable from C alone (the H2 anti-leak: a genuine forward step, not a lookup). Construction is blind because the splitter is deterministic from seed and runs BEFORE any model sees C — no human picks what to hide per item. THREE control arms minted the same way: (a) ALREADY-A-STONE control: C contains everything needed to compute T (T IS derivable) -> must show ~zero earned bits (the lookup-vs-forecast separator); (b) ALEATORIC control: T = next term of a no-rule RANDOM sequence (seeded RNG, no generator rule) -> any high confidence here is a calibration FAILURE; (c) the structured forward bubbles (T withheld but rule-constrained to a small answer set).

- **confidence_source:** DERIVED, never elicited 'sharpness' (honoring the locked guardrail). TWO channels, split by what each runner exposes (both VERIFIED LIVE this session): CHANNEL-LP (the rigorous one) for forced-choice / single-token-answer targets on LOGPROB-CAPABLE models — gpt-4.1-mini, gpt-4o-mini, gpt-4.1 ALL returned logprobs+top_logprobs LIVE this session. We constrain T to a small answer set (e.g. mod-97 -> the answer is one of K pre-listed candidates, or a yes/no/letter) so the model's first answer-token logprob IS a calibrated probability: confidence c = softmax-prob of the chosen answer token among the top_logprobs candidates. This is a real proper-scoring probability, not a self-report.
